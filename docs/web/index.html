Qué es AIF

PRODUCT.md · visión v0.1

AIF — Agent Interaction Forms — dota a las herramientas de software de una interfaz de interacción autodescriptiva, determinista y orientada a agentes. La finalidad es que un agente pueda usar una herramienta sin descubrir constantemente cómo funciona, qué información necesita o cómo corregir una petición incorrecta: la propia herramienta se lo comunica de forma estructurada.

El problema

Las herramientas tradicionales están diseñadas principalmente para ser utilizadas por personas. Cuando un agente necesita usarlas, frecuentemente tiene que consultar documentación, interpretar mensajes de error, descubrir parámetros, reconstruir peticiones y realizar invocaciones adicionales.

Eso introduce incertidumbre, consume contexto y aumenta el esfuerzo necesario para completar una operación. AIF propone que sea la herramienta, y no el agente, quien tenga la responsabilidad de describir sus necesidades de interacción.

Qué no es AIF. No es un agente, ni un orquestador, ni un gestor de workflows, ni un sistema de formularios gráficos. Tampoco sustituye la lógica de negocio: su responsabilidad se limita a facilitar la interacción. Dónde queda la autoridad.

2

Cómo funciona

PRODUCT.md §3

Tres situaciones habituales. La herramienta decide en cada petición cuál aplica y lo comunica de forma estructurada.

Información completa

Ejecuta

Los datos son suficientes y válidos. La herramienta ejecuta la operación y devuelve el resultado de su dominio.

Información incompleta

Devuelve el formulario

Indica qué información necesita, qué valores admite y qué datos válidos ya recibió. Nada se ejecutó.

Información incorrecta

Permite corregir

Identifica los errores, devuelve los campos conocidos presentes que no son sensibles ni están rechazados e indica cómo continuar.

El formulario no es una interfaz gráfica. Es una respuesta estructurada que el agente interpreta directamente.

Un ejemplo sencillo

Un agente solicita crear una tarea titulada «Revisar documentación». La herramienta necesita conocer también su prioridad. En lugar de devolver un error genérico, le comunica:

  • Título recibido: Revisar documentación.
  • Información pendiente: prioridad.
  • Valores admitidos: baja, media y alta.

El agente completa la información y vuelve a solicitar la operación. Si hubiera proporcionado todos los datos correctamente desde el principio, la operación se habría ejecutado en una única invocación.

Principio fundamental: una necesidad, una invocación siempre que la información disponible sea suficiente.

3

Las dos modalidades

PRODUCT.md §4

Dos formas complementarias de llevar AIF a una herramienta. Comparten el mismo núcleo y el mismo contrato de interacción.

Disponible en Go

Integración nativa

La biblioteca AIF se incorpora directamente al código fuente de una aplicación. La herramienta adquiere las capacidades de interacción sin necesitar un ejecutable intermediario.

Por ejemplo, Tasks-AI podría incorporar la biblioteca dentro de su propio ejecutable Go, conservando íntegramente su lógica de negocio.

Conceptual · pendiente de diseño

Integración externa

Un ejecutable AIF actúa como intermediario entre el agente y una herramienta existente. Un archivo de definición describe las operaciones disponibles, la información necesaria, sus restricciones y cómo invocar la herramienta.

Permite adaptar herramientas sin modificar su código, siempre que dispongan de una interfaz invocable y sus resultados puedan interpretarse de forma fiable.

La modalidad externa es conceptual. AIF CLI como producto y AIF Definition están pendientes de diseño: esta página describe su responsabilidad, no una sintaxis. Lo que hoy está disponible es la integración nativa en Go.

Uso e integración de la biblioteca Go

aif.go · handle.go · response.go

La implementación de referencia es un paquete Go sin dependencias externas. Quien lo integra declara sus operaciones y usa Handle para comprobar la estructura de las peticiones. Su sistema conserva las reglas, los permisos y el almacenamiento.

API pública de la biblioteca
SímboloResponsabilidad
aif.OperationIdentificador, descripción de una línea, campos y función Execute.
aif.FieldRequired, Type, Allowed, Description, Schema, Sensitive y el hook Validate para reglas finas.
aif.Executor{Operations}Conjunto fijo de operaciones que el ejecutor atiende.
(*Executor).Handle([]byte)Parsea el sobre, comprueba límites y versión, valida campos y ejecuta. Nunca entra en pánico con entrada malformada.
aif.ResponseResultado tipado. json.Marshal usa su MarshalJSON, que emite solo los miembros del resultado.
aif.DeniedErrorConvierte un error de Execute en denied con reason.
aif.DomainErrorConvierte un error de Execute en failed con message y code.
aif.InvalidErrorConvierte una regla de dominio que rechaza al ejecutar en invalid reparable con Fields; se declara antes de cualquier efecto.
aif.MaxInputBytes · aif.MaxDepthLímites declarados por esta implementación: 256 KiB y profundidad 32.
 
package main

import (
	"encoding/json"
	"fmt"

	"github.com/fred66sp/agent-interaction-forms"
)

func main() {
	op := &aif.Operation{
		ID:          "record_observation",
		Description: "Registra una observación con título y tipo.",
		Fields: []aif.Field{
			{Name: "title", Required: true, Type: "string",
				Schema: json.RawMessage(`{"maxLength":40}`)},
			{Name: "kind", Required: true, Type: "string",
				Allowed: []string{"learning", "decision", "discovery", "bugfix"}},
			{Name: "contact", Type: "string", Sensitive: true},
		},
		Execute: func(input map[string]json.RawMessage) (json.RawMessage, error) {
			// El dominio ejecuta su efecto y devuelve datos opacos.
			return json.RawMessage(`{"id":"obs_0001"}`), nil
		},
	}
	executor := aif.Executor{Operations: []*aif.Operation{op}}

	// La petición llega como bytes: CLI, HTTP o cola; el contrato no cambia.
	raw := []byte(`{"aif":"0.2","operation":"record_observation",
		"input":{"kind":"learning"}}`)
	resp := executor.Handle(raw)

	// MarshalJSON emite exactamente los miembros que exige §3.
	out, err := json.Marshal(resp)
	if err != nil {
		panic(err)
	}
	fmt.Println(string(out))
}

Con esa petición, el programa escribe una respuesta input_needed: missing contiene title, collected incluye kind —presente, no nulo, no sensible y no rechazado— y fields describe los tres campos declarados, incluido el opcional y sensible contact. El nombre de contact aparece como descriptor; su valor nunca se devuelve. collected no certifica validez: es la copia de lo aportado.

Qué pone el integrador y qué pone AIF

AIF

El sobre (el objeto JSON de la petición) y la mecánica

  • Comprueba tamaño, profundidad, claves duplicadas, aif, versión, miembros de la raíz fuera del sobre y tipo de operation e input.
  • Resuelve la operación y valida Type, Allowed y el hook Validate de cada campo; puede hacerlo de forma progresiva o exhaustiva e informa de todos los problemas detectados, sin prometer detección exhaustiva.
  • Aplica exclusividad, precedencia y omisión de sensibles; collected copia los campos conocidos presentes, no nulos, no sensibles y no rechazados, sin certificar su validez.
  • Serializa los miembros del resultado de forma determinista.
Integrador

El dominio y sus reglas

  • Declara los campos una sola vez y qué regla fina publica cada Schema.
  • Escribe en Execute solo lo que AIF no puede expresar: reglas de negocio, permisos, persistencia y transacciones.
  • Devuelve DeniedError para una denegación y DomainError para un fallo con código; InvalidError cuando una regla de dominio rechaza el input antes de cualquier efecto.
  • Marca con Sensitive lo que no debe volver en ninguna respuesta.

No construyas el JSON a mano. Usa json.Marshal(resp): el MarshalJSON del paquete elige los miembros según result y omite los que no corresponden. Construir el mapa por tu cuenta duplica el contrato y abre la puerta a respuestas que dicen dos cosas a la vez.

Perfil CLI y códigos de salida

cmd/aifdemo/main.go · §7

El perfil CLI adapta el contrato a herramientas de línea de comandos sin ampliar sus reglas básicas. La herramienta de demostración aifdemo ofrece la operación record_observation y muestra cómo consultar operaciones, corregir datos, continuar y leer los códigos de salida. Lo descrito aquí es esa herramienta; el AIF CLI como producto, con AIF Definition, sigue pendiente de diseño.

  • No interactiva. Lee una petición de stdin, escribe exactamente un objeto JSON con salto de línea final en stdout y manda diagnósticos y avisos a stderr.
  • El código depende solo del resultado. Es determinista; stderr no lo altera. El descubrimiento también sale con 0.
  • Continuación = nueva invocación con el input íntegro y corregido. El ejecutor no reserva estado entre invocaciones.
  • Un invalid señalado en Execute sigue siendo reparable. El dominio lo declara antes de cualquier efecto, la CLI sale con 2 y el reenvío corregido ejecuta.
CL-04 · códigos de salida del perfil CLI
CódigoresultLectura para el agente
0executed y descubrimientoHay efecto completado o lista de operaciones.
1failedFallo del dominio o de infraestructura; estado posiblemente desconocido.
2input_needed, invalidLa petición es reparable: completar o corregir y reenviar.
3unsupported_version, malformed_request, unknown_operationProblema de contrato: versión, sintaxis u operación. No hay nada que reparar campo a campo.
4deniedEl dominio niega la operación; no es un trámite reparable.
 
go build -o aifdemo ./cmd/aifdemo

printf '%s' '{"aif":"0.2","operation":"record_observation","input":{"kind":"learning"}}' \
  | ./aifdemo
# stdout: una respuesta input_needed con missing, fields y collected
# exit: 2
# La operación ejecuta si AIF_DEMO_STORE apunta a un fichero JSON Lines.
AIF_DEMO_STORE=/tmp/observaciones.jsonl \
  ./aifdemo < peticion.json

# Precondiciones de dominio para los escenarios de error:
# AIF_DEMO_DENY_WRITE=1  → denied  (exit 4)
# AIF_DEMO_STORAGE_FAIL=1 → failed (exit 1)
¿Por qué tres resultados comparten el código 3?

Porque comparten la misma consecuencia operativa para el consumidor: el contrato no permite ejecutar y no hay campos que corregir. La distinción accionable sigue estando en result: versión no soportada (supported), entrada no interpretable (reason) u operación inexistente (known_operations).

Separar la causa es trabajo del miembro result; el código de salida solo clasifica la reparabilidad para scripts. Por eso input_needed e invalid sí comparten el 2: ambos piden una petición nueva con el input completo.

Cuidado con go run. go run devuelve 1 cuando el programa sale con cualquier código distinto de 0. Para observar los códigos reales 0/1/2/3/4, compila el binario y ejecútalo directamente.

PoC real con ACM

poc/acm/ · 4 escenarios

La prueba de concepto (PoC) conecta la biblioteca con el adaptador real de ACM y usa una memoria temporal. No cambia las reglas de ACM ni toca la memoria de producción: trabaja con una copia intacta y ejecuta la operación learning en un proceso separado.

El acmpoc de esta PoC ejercita el perfil CLI de AIF (el mismo mecanismo que usará la futura integración externa, aún sin sintaxis decidida). AIF decide el sobre, la estructura de campos y el conjunto cerrado de confidence; ACM conserva su validación, su deduplicación por contenido (content_hash), la idempotencia de form_id, el ETag y las transacciones. El outcome es la respuesta de ACM, sin reinterpretar.

Las garantías que se prueban son de ACM, no de AIF. La deduplicación, la idempotencia real y las transacciones siguen siendo del adaptador. AIF solo comprueba que su vocabulario puede envolver esa operación sin robarle autoridad ni prometer garantías que no existen en el contrato.

8

Los dos papeles del contrato

SPECIFICATION §1, §5, §6

Cada petición debe contener todos los datos que necesita la herramienta, que vuelve a comprobarlos en cada llamada. El contrato no guarda una sesión ni define un identificador de formulario o una relación entre llamadas.

Los dos papeles del contrato
PapelQué haceQué no decide
Consumidor · agenteCompone la petición, lee el result, corrige o completa el input y reenvía la operación completa.No concede permisos ni sustituye la validación del dominio.
Ejecutor · herramientaDeclara operaciones y campos, valida, ejecuta el efecto y elige el resultado que describe lo ocurrido.No puede declarar executed si el efecto no se completó.
  • Camino directo. Si el consumidor ya dispone de todos los datos, invoca la operación y recibe executed sin ningún intercambio previo impuesto por AIF.
  • Una sola estructura. Todos los resultados usan la misma estructura JSON. El campo result indica cuál de los ocho resultados se ha producido.
  • Datos, no prosa. Solo result y los miembros exigidos por la especificación son fiables para decidir cómo continuar. Interpretar texto libre es un error de conformidad.
  • Comprobación completa y sin estado. El result de la petición anterior no concede ningún derecho: cada petición es stateless, la herramienta vuelve a comprobar todo el input y el dominio lo valida íntegramente antes de producir efectos.
  • Ni permisos ni pruebas de ejecución. Una respuesta AIF no autoriza ni demuestra que algo se ejecutó; esas garantías se obtienen del dominio.
  • Rechazo explícito. Los miembros desconocidos de input se rechazan como invalid; el silencio ante un nombre mal escrito ocultaría errores del consumidor. En las respuestas, en cambio, las extensiones son toleradas y el consumidor debe ignorar lo que no reconozca.

Diseñado para agentes. «Agent-first» significa que el contrato permite al agente decidir a partir de datos comprobables: qué falta, qué es inválido, qué se conservó y cuál fue el resultado. La documentación de cada operación sigue siendo responsabilidad del sistema que la ofrece.

9

Flujo de validación y reparación

SPECIFICATION §5, §7 CL-06

La herramienta comprueba cada petición antes de actuar. Si los datos son válidos, puede ejecutar la operación; si faltan datos o hay errores, responde con la información necesaria para corregirla.

Qué define la continuación

  • Tras input_needed o invalid, la siguiente petición válida es la misma operación con un input completo: los valores de collected, los que el consumidor añada y una corrección por cada campo de invalid.
  • collected es copia de lo aportado: todos los campos conocidos presentes, no nulos, no sensibles y no rechazados. No certifica validez ni exime de corregir los campos de invalid. fields y description son información para elegir valores, no datos que reenviar.
  • Tras denied, failed o un error de contrato, AIF no define continuación: decide el consumidor con la información del resultado y la documentación del dominio.
  • Reenviar puede repetir el efecto. Cada envío es una petición nueva y sus efectos dependen del sistema. Ninguna respuesta AIF garantiza autenticidad, ejecución única ni que sea seguro reintentar.

Si los datos están completos, se actúa directamente. AIF no exige rellenar un formulario antes de cada operación. La respuesta para corregir datos se usa cuando la petición no puede ejecutarse.

Las respuestas de descubrimiento son la excepción deliberada: se producen cuando la petición omite operation y no llevan result ni operation. No son un noveno resultado, sino otra forma del sobre (§7, CL-05).

Forma de los resultados que no reparan

Los cinco resultados restantes no comparten miembros de campos: cada uno informa de lo que el agente necesita para decidir si detenerse, informar o cambiar de contrato.

{"aif":"0.2","operation":"record_observation","result":"denied",
 "reason":"el consumidor no tiene permiso de escritura sobre el dominio"}
{"aif":"0.2","operation":"record_observation","result":"failed",
 "message":"el almacenamiento rechazó la escritura; estado desconocido, la observación no queda registrada",
 "code":"storage_unavailable"}
{"aif":"0.2","result":"unsupported_version","supported":["0.2"]}
{"aif":"0.2","result":"malformed_request",
 "reason":"carece de aif",
 "supported":["0.2"]}
{"aif":"0.2","operation":"no_existe","result":"unknown_operation",
 "known_operations":["record_observation"]}
¿Por qué ocho resultados y no un código de error con subcódigos?

Porque cada resultado cambia la decisión del agente. Reparar (input_needed, invalid), detenerse (denied), informar de un fallo real (failed) y corregir el contrato (unsupported_version, malformed_request, unknown_operation) son continuaciones distintas. Un código anidado obligaría al consumidor a interpretar una jerarquía que el contrato no define.

La separación entre unsupported_version y malformed_request es de causa: la primera declara una versión que el ejecutor no soporta; la segunda ni siquiera establece el contrato. Y unknown_operation existe para que el agente pueda elegir entre las operaciones declaradas en known_operations. Esta versión solo reconoce el literal "0.2": "0.1" también recibe unsupported_version.

Una respuesta, un sentido. input_needed, invalid, denied y los tres errores de contrato no producen efecto de dominio; el invalid que el dominio señala en Execute se declara antes de actuar y tampoco deja efecto. failed tampoco puede presentarse como executed: si el ejecutor duda, lo dice.

Estructura de los mensajes JSON

SPECIFICATION §1, §7 CL-05

Las peticiones y respuestas son objetos JSON (RFC 8259). No se usan XML, formularios binarios ni un lenguaje de expresiones. La misma estructura sirve para una herramienta de línea de comandos (CLI), una función local u otro medio elegido por quien la integre.

Petición · miembros del sobre
MiembroCondiciónContenido
aifDEBEVersión del contrato. Literal "0.2" en esta versión.
operationPUEDE faltar solo para descubrimientoIdentificador textual de la operación.
inputPUEDE faltarObjeto con los datos, campo a campo. Puede ser null: equivale a vacío.

La petición admite solo esos tres miembros de raíz. Cualquier otro responde malformed_request con un reason que nombra la clave, sea o no un campo de la operación pedida: los datos de la operación van dentro de input. La regla alcanza también al descubrimiento.

Respuesta de operación · miembros comunes
MiembroCondiciónContenido
aifDEBEVersión empleada para responder.
operationDEBE, salvo en unsupported_version y malformed_requestEco del identificador solicitado.
resultDEBEUno de los ocho resultados de §2.
 
{"aif":"0.2","operation":"record_observation",
 "input":{"title":"Perfil CLI decidido","kind":"decision","confidence":"confirmed"}}
{"aif":"0.2","operation":"record_observation","result":"executed",
 "outcome":{"id":"obs_0142","recorded_at":"2026-11-24T19:41:00Z"}}

AIF no define la estructura de outcome. El agente puede tratarlo como un dato cuyo contenido no necesita interpretar o utilizarlo según la documentación de la operación. Qué hacer después de executed también depende del sistema, no de AIF.

Descubrimiento

Si la petición omite operation, el ejecutor responde con la lista de operaciones y una descripción de una línea. request es la plantilla de emisión: se sustituye <id> por el identificador elegido y input se rellena con los campos de la operación. Esta respuesta no es una operación: no lleva result ni operation en la raíz.

{"aif":"0.2"}
{"aif":"0.2","request":{"aif":"0.2","operation":"<id>","input":{}},
 "operations":[
  {"id":"record_observation",
   "description":"Registra una observación con título, tipo y confianza."}]}

Extensiones toleradas, miembros críticos acotados. Una respuesta puede incluir miembros que AIF no define; el consumidor debe ignorar los que no reconozca. Lo que el ejecutor no puede hacer es colocar fuera de los miembros definidos información de la que dependa la decisión del agente. En input ocurre lo contrario: un miembro desconocido invalida la petición.

Campos, reglas y datos conservados

SPECIFICATION §3.2, §4

Cuando faltan datos o hay errores, la respuesta describe los campos y sus reglas. Así, el agente sabe qué corregir. collected devuelve los campos conocidos presentes, no nulos, no sensibles y no rechazados; su presencia no certifica validez.

Descriptor de campo (§4) y problema de campo (§3.2)
MiembroClaseSentido
requiredimprescindibletrue si el ejecutor no puede ejecutar sin el valor.
valuecontextualValor recibido en esta petición, salvo que sea sensible.
reasoncontextualPor qué el valor es inválido; solo dentro de invalid.
typeopcionalstring, number, boolean, object o array.
allowedopcionalValores permitidos cuando el conjunto es cerrado.
descriptionopcionalIndicación contextual en texto; no sustituye a una regla mecánica.
schemaopcionalFragmento JSON Schema 2020-12 de la regla. Obligatorio cuando la regla se expresa fielmente con esa sintaxis y no con type ni allowed; si no se expresa fielmente, la regla va en reason y schema puede omitirse.

Reglas que no admiten interpretación

  • Ausencia frente a invalidez. missing e invalid son excluyentes por campo: un campo no figura en ambos. Una petición puede tener los dos problemas y recibe una única respuesta con ambos informes.
  • Si hay varios problemas. Si hay al menos un campo inválido, el resultado es invalid; si no lo hay y faltan campos obligatorios, es input_needed.
  • Validación progresiva o exhaustiva. El ejecutor puede detenerse en el primer problema de cada campo o recorrer todas las reglas; en ambos casos informa de todos los problemas que detecta. La respuesta no promete detección exhaustiva.
  • Todo valor proporcionado se valida, sea de un campo obligatorio u opcional. El fallo de un opcional se reporta igual que el de un obligatorio.
  • collected es obligatorio en las respuestas reparables. Contiene todos los campos conocidos de la operación que la petición trae presentes con valor distinto de null, no sensibles y no rechazados. No certifica validez: es copia de lo aportado. Las únicas omisiones legítimas son las de valores sensibles y las de campos rechazados que figuran en invalid; omitir un campo conocido presente, no nulo, no sensible y no rechazado rompe la garantía y es un defecto de conformidad.
  • Los valores sensibles no vuelven en ningún miembro: ni en collected, ni en value, ni en reason, ni en message, ni en outcome, ni en description.
  • schema se publica, no se evalúa. Su sintaxis es la de JSON Schema 2020-12, reutilizada tal cual. AIF no añade un lenguaje de validación ni un motor; quien valida es el dominio. Lo declarado debe expresar el comportamiento que realmente se comprueba. Si la regla no se expresa fielmente con schema, deja de ser obligatorio: reason la expone y schema puede omitirse o limitarse a la parte que sí expresa.
{"aif":"0.2","operation":"record_observation","result":"input_needed",
 "missing":["title","confidence"],
 "fields":{"title":{"required":true,"type":"string",
                   "description":"Título breve de la observación"},
           "confidence":{"required":true,"type":"string",
                         "allowed":["hypothesis","confirmed"]}},
 "collected":{"kind":"learning"}}
{"aif":"0.2","operation":"record_observation","result":"invalid",
 "invalid":{"kind":{"value":"Learning",
                    "reason":"valor no permitido",
                    "allowed":["learning","decision","discovery","bugfix"]}},
 "fields":{"kind":{"required":true,"type":"string",
                   "allowed":["learning","decision","discovery","bugfix"]}},
 "collected":{"title":"Perfil CLI decidido","confidence":"confirmed"}}

Cuando la petición mezcla campos ausentes e inválidos, la respuesta sigue siendo una sola. La exclusividad se aplica campo a campo, no al documento:

{"aif":"0.2","operation":"record_observation","result":"invalid",
 "missing":["confidence"],
 "invalid":{"kind":{"value":"Learning",
                    "reason":"valor no permitido",
                    "allowed":["learning","decision","discovery","bugfix"]}},
 "fields":{"title":{"required":true,"type":"string",
                    "description":"Título breve de la observación"},
           "kind":{"required":true,"type":"string",
                   "allowed":["learning","decision","discovery","bugfix"]},
           "confidence":{"required":true,"type":"string",
                         "allowed":["hypothesis","confirmed"]}},
 "collected":{"title":"Perfil CLI decidido"}}
¿Por qué collected no es opcional?

Porque el objetivo es corregir sin reconstruir. Si el ejecutor pudiera omitir campos conocidos presentes, no nulos y no rechazados sin explicación, el agente no sabría si el dato se perdió, si no se leyó o si debe volver a enviarlo. La omisión solo se permite por sensibilidad, y esa omisión no significa nada más: no convierte el valor en inválido ni en ausente.

collected es copia de lo aportado y no certifica validez; fields es información para elegir valores nuevos, no datos que reenviar.

Las reglas que no se expresan con type ni allowed se declaran en schema cuando JSON Schema 2020-12 las expresa fielmente. Este ejemplo muestra la regla que causó el rechazo:

{"aif":"0.2","operation":"record_observation","result":"invalid",
 "invalid":{"title":{"value":"Perfil CLI decidido durante la revisión final de la especificación",
                     "reason":"supera la longitud máxima",
                     "schema":{"maxLength":40}}},
 "fields":{"title":{"required":true,"type":"string",
                    "schema":{"maxLength":40}}},
 "collected":{"kind":"learning","confidence":"confirmed"}}

Los valores legítimos no se confunden con ausencia. false, 0, "" y [] se validan como cualquier otro valor. Solo la ausencia del miembro o su valor null cuentan como campo no aportado.

Responsabilidades, seguridad y límites

SPECIFICATION §6 · L-01…L-05

El contrato describe la interacción; el ejecutor y su dominio retienen toda la autoridad. Esta separación no es una recomendación de estilo: es el límite que impide que una respuesta JSON se convierta en permiso o en prueba de ejecución.

Quién retiene qué (§6)
QuiénRetiene
Ejecutor y dominioReglas de negocio, validación efectiva, autorización y permisos, ejecución, persistencia, integridad, transacciones y cualquier garantía de idempotencia que exista.
AIFÚnicamente el vocabulario de §§1–5 para que esa autoridad se comunique.
  • L-01 · Sin autorización implícita. Los datos de una respuesta AIF no son autorización ni evidencia de ejecución. Toda continuación la revalida el ejecutor.
  • L-02 · Sin efecto en los rechazos. Entrada inválida o denegada no produce efecto de dominio, y el resultado debe permitir comprobarlo. El invalid que el dominio señala al ejecutar se declara antes de actuar y no deja efecto.
  • L-03 · Sin valores sensibles. El ejecutor no devuelve un valor sensible en ningún miembro. La sensibilidad la declara el dominio. En collected las únicas omisiones legítimas son las de valores sensibles y las de campos rechazados que figuran en invalid.
  • L-04 · Límites declarados. El ejecutor documenta los límites de tamaño y profundidad de su input. La especificación no fija números: exige declararlos. Esta implementación usa 256 KiB y profundidad 32.
  • L-05 · Prosa honesta. outcome, reason y message son del dominio; AIF solo exige su presencia y que no mientan sobre el estado del efecto.
Límite de entrada

256 KiB

Se comprueba antes de parsear. Una entrada mayor responde malformed_request con reason determinista.

Límite de forma

Profundidad 32

El escáner rechaza anidamiento excesivo y claves duplicadas, que encoding/json por sí solo no detecta.

Diagnóstico

Causa, no prosa

reason identifica una causa mecánica: entrada vacía, JSON inválido, no es un objeto, carece de aif, tipo incorrecto, claves duplicadas o un miembro de la raíz fuera del sobre, que se nombra.

Publicar un schema no es validar con él. La biblioteca transporta el fragmento JSON Schema 2020-12 tal cual y no ejecuta un motor. Si una regla no se comprueba de verdad, publicarla sería una promesa falsa: el contrato exige que lo declarado exprese el comportamiento real del dominio. Cuando la regla no se expresa fielmente con esa sintaxis, reason la expone y schema puede omitirse o limitarse a la parte que sí expresa.

Resultados y limitaciones del experimento

docs/experiment/EXPERIMENT-RESULTS.md

Antes de la Specification se realizó un experimento de viabilidad: 3 escenarios × 5 pares × 2 variantes = 30 mediciones, para comparar ACM con una CLI JSON competente. Esta sección cuenta lo ocurrido; no mide la adopción ni representa una decisión de producto.

Resultado: INCONCLUSO. Según la regla 2 del PRD §7, una medición incompleta o no comparable se clasifica como INCONCLUSO. En 9 de las 20 ejecuciones de reparación no se entregaron los datos previstos del usuario. Esto incumplió una condición del experimento y afectó a la medición del éxito. Se completaron las 30 mediciones, pero no sustentan ninguno de los criterios de decisión.

Limitaciones que acotan la lectura

  • Condición experimental vulnerada. El fixture de usuario no se entregó en 9 de 20 reparaciones (5 AIF y 4 CLI) aunque el modelo pedía el dato. La comparación de éxito no es válida.
  • Temperatura efectiva no ejecutada. Se configuró a 0 y la configurabilidad del proveedor estaba acreditada, pero la comprobación directa exigía modificar configuración global no autorizada.
  • Caché de lectura compartida con la máquina. El contenido cacheado del prompt del sistema es simétrico entre variantes, pero no replicable en otra máquina.
  • Instrumento artesanal. Dos defectos documentados: un contador de errores de contrato por escapado (corregido y re-verificado) y el detector del fixture (asumido sin corrección), que acota la confianza en cualquier medición automática de interacción agente-herramienta.
  • Comportamientos genuinos del modelo. Reenvíos con duplicate_count=2, bodies inventados y el texto del fixture pegado como body aparecen en los datos brutos.

Lo que este experimento no dice. No demuestra que AIF sea superior a una CLI JSON competente, ni mide adopción, productividad o rendimiento en producción. Tampoco autoriza a extrapolar los 8/15: la campaña no es comparable y no se usa como argumento de producto.
